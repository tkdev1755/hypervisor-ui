L'API refuse toute requête sans jeton. À la connexion, elle en donne deux : • l'access token (15 minutes), envoyé à chaque requête dans l'en-tête Authorization: Bearer …. On le garde en mémoire (un signal) : il disparaît à la fermeture de l'onglet et un script malveillant ne peut pas le lire dans le stockage du navigateur ;
• le refresh token (7 jours), qui sert à en obtenir un nouveau sans redemander le mot de passe. Il est gardé dans sessionStorage pour qu'un rechargement de la page ne déconnecte pas. Personne n'ajoute ces jetons à la main : l'intercepteur le fait pour toutes les requêtes, et rattrape les jetons expirés. Les gardes de routes (authGuard, adminGuard) décident si une page peut s'afficher. L'interface cache les boutons interdits, mais c'est l'API qui fait respecter les droits (403 ou 404) : cacher n'est que du confort. Si dix requêtes échouent en même temps avec un jeton expiré, il ne faut surtout pas lancer dix refresh : le deuxième échouerait et déconnecterait l'utilisateur. C'est le rôle de shareReplay dans refresh() (leçons 16 et 17) : toutes les requêtes attendent le même refresh, puis sont rejouées une fois. Un 401 sur « changer mon mot de passe » signifie « l'ancien mot de passe est faux », pas « jeton expiré ». Le mapper d'erreurs fait la différence (SESSION_EXPIRED contre INVALID_CREDENTIALS) ; l'intercepteur s'appuie sur lui. Sans cela, une faute de frappe déconnecterait l'utilisateur. Lisez votre profil, puis forcez un refresh : le journal montre les appels, et vous restez connecté.
